# MyStash — Build Plan

See [../README.md](../README.md) for the project overview and [SPECIFICATIONS.md](SPECIFICATIONS.md) for tech stack, app flow, datastore layout, and UI/UX spec. This document breaks the build into phases, each made up of small, independently-checkable objectives.

## Phase 0 — Environment & Dependencies

Get the Docker/PHP environment able to do the two things the whole app depends on: encode video to MP4/H.265 and create password-protected 7zip archives.

- [x] 0.1 Base Dockerfile: PHP + web server (php-fpm/nginx or php built-in server for dev) — `App/Dockerfile`, `docker-compose.yml`. Started as `php:8.3-cli` with the built-in server; now nginx in front of `php:8.3-fpm`, because the built-in server is single-threaded and that turned out to matter a great deal (see 7.5)
- [x] 0.2 Install `ffmpeg` in the container; verify `ffmpeg -version` and `ffprobe -version` from PHP via `exec` — verified via `App/src/VideoEncoder.php`
- [x] 0.3 Install `p7zip-full` (provides `7z` CLI) in the container; verify `7z` from PHP via `exec` — verified via `App/src/Crypto7z.php`
- [x] 0.4 PHP wrapper function: encode an input video to MP4/H.265 via `ffmpeg` (`-c:v libx265`), return success/failure + output path — `App/src/VideoEncoder.php`
- [x] 0.5 PHP wrapper function: create an AES-256-encrypted `.7z` archive from a file/directory with a password, using `proc_open` and compression level `-mx=0` (store only — 7zip is for encryption here, not compression; recompressing already-compressed video wastes CPU and slows load) (password passed via stdin or a temp arg array — never interpolated into a shell string) — `App/src/Crypto7z.php`
- [x] 0.6 PHP wrapper function: extract a password-protected `.7z` archive, return success/failure (used for login check) — `App/src/Crypto7z.php`
- [x] 0.7 Smoke test script: round-trip `App/Data/TestUser/videos/1.mp4` (existing sample fixture) through encrypt → extract → compare, and through ffmpeg conversion — `App/tests/smoke_test.php`, all 11 checks passing

### Phase 3 follow-ups (from idea review)

- [x] 3.8 Rebuild the preview clip as a **timelapse**, per SPECIFICATIONS.md §2.3: sample one frame every 15s across the whole video and join them into a short silent clip — `VideoEncoder::buildPreviewClip()`. Done in two ffmpeg passes (sample stills, then join at 4fps); a single pass using `setpts`/`-r` silently dropped most sampled frames. Verified: a 62s source now yields a 4-frame, 1s, 480px-wide clip spanning the whole video instead of a continuous excerpt.
- [x] 3.9 **Set the preview image, and change it afterwards** — `App/src/VideoPreview.php`, `App/public/video_preview.php`, and a Preview Image card on the video edit screen. The frame was chosen once at upload from a timestamp and then fixed for good: if it landed on a fade or a blurred pan, the tile wore it forever. There are now two ways to set it and both work at upload time *and* afterwards — take a frame from a different point, or supply a picture that is not in the video at all.

  - **The preview goes through `Crypto7z::replace()`, never `encrypt()`.** `{ID}.jpg.preview.enc` is the only copy of that image, and `encrypt()` deletes its destination before writing (4.29) — so a failed re-preview would leave the video with no thumbnail rather than the one it already had. Every refusal is covered by a test asserting the previous archive is byte-for-byte unchanged.
  - **Whatever is uploaded is re-encoded to JPEG**, capped at 1280px on the longest edge, because the archive is named `.jpg.preview.enc` and `media.php` serves it as `image/jpeg` — the same "the filename describes the actual bytes" rule as the creator avatars (4.10). Bigger than the avatars' 512px: this is the wall tile *and* the poster behind the watch page's player, so it has to survive being shown large.
  - **The uploaded bytes are never served back.** What is stored is ffmpeg's re-encode of the pixels, which doubles as the validation — a file that is not an image fails there and nothing is written, and a file that is an image *and also* something else arrives as a plain JPEG with whatever was riding along in the container gone.
  - **`preview_capture_seconds` becomes null when the picture was supplied**, rather than keeping the timestamp it used to be taken from — the edit screen displays that field, and leaving a stale number there would make it lie about where the current picture came from.
  - **A picture that will not decode does not fail the whole upload.** At ingest it falls back to the capture time: the video has already been transferred, and losing it over a thumbnail would be a poor trade. From the edit screen, where nothing else is at stake, it is refused with a message.
  - **Taking a frame has to decrypt the video first**, so it is not the cheap metadata edit it looks like. That is the same work `media.php` does to play the video, so it is not a new cost — but it is why the card says so.

- [x] 3.10 **Video IDs are claimed atomically** — found while testing 3.9. `Datastore::nextVideoId()` derives the next id from the *index*, so two uploads that both start before either has saved compute the same id, and the second encrypts its files straight over the first's — losing that video outright. `VideoIngest` now claims the directory with `mkdir()` before writing anything into it and walks to the next id if it is taken, which is an atomic test-and-set: whoever creates the directory owns the id. The single-threaded built-in server serialised requests and made this unreachable; nginx in front of php-fpm (7.5) does not. It first surfaced as a bare `mkdir(): File exists` warning in a test, which is the kind of thing worth chasing rather than silencing.

- [x] 4.28 **Conversion runs in the background now.** Pressing Convert used to run `ffmpeg` synchronously inside the request. On the single-threaded built-in server that did not merely make that one request slow — every other page, thumbnail and media range request queued behind the transcode, and the whole app stopped answering until the container was restarted (observed as `NS_ERROR_NET_EMPTY_RESPONSE` on the convert POST). The data-loss half was split out as 4.29 and shipped first.

  `video_convert.php` no longer converts anything. It validates, starts a job, and redirects — the transcode happens in `App/bin/job_worker.php`, detached, and the watch page polls `job_status.php` and draws a bar. The job mechanism is shared with 6.6 rather than grown twice; see 7.5 for the container change underneath it.

  What is worth recording about the conversion specifically:

  - **Progress is ffmpeg's own.** It is asked for `-progress pipe:1`, which emits machine-readable `out_time_us=` as it encodes, rather than scraping the human stderr banner. The duration is known up front from `ffprobe`, so the bar is a real percentage. Before the first frame there is no honest number to show, so the bar sweeps instead of sitting at zero looking wedged.
  - **The timeout is a stall timer, not a total.** A 90-minute video legitimately takes a long time, and a ceiling short enough to catch a wedged `ffmpeg` would kill a healthy one. What is never normal is `ffmpeg` sitting at the same timestamp for minutes, so that is what gets killed (default 180s of no movement, with a very generous absolute backstop). A killed run has touched nothing: the archive is only replaced after a complete, verified conversion (4.29).
  - **A second press cannot start a second run.** The job id is derived from the user and the video id, so pressing Convert again finds the existing job instead of launching another `ffmpeg` over the same archive. The button is also gone from the page while one runs — not merely disabled, because offering it would be a lie.
  - **A worker that dies is reported as failed, not as running forever.** The job record cannot be trusted to say so — a killed process writes nothing — so liveness comes from an `flock` the worker holds for its whole life, which the kernel releases however it exits.

- [x] 4.29 **Nothing overwrites the only copy of anything any more** — `Crypto7z::replace()`. `encrypt()` *deletes its destination before writing the replacement*, so pointing it at a live archive opens a window where the file does not exist at all; if the write then fails, returns `false` unnoticed, or is interrupted, it never comes back. `video_convert.php` did exactly that to `{ID}.mp4.enc`, with the decrypted original existing only in tmpfs and wiped by the `finally` — the one place in the app where a routine click could lose a video outright.

  `replace()` does what re-keying already did in 6.2/6.4: encrypt beside the archive under a per-call name, **verify** the result really opens and holds the same bytes (extract it and compare sha256 — an encrypt that reports success can still have truncated), swap it in, and keep the previous bytes as `.old` until the swap succeeds, restoring them if any step fails.

  Two callers changed, and the second matters more than the one that prompted this:

  - **`video_convert.php`** now calls `replace()` and *checks the result*. A failure leaves the video exactly as it was, still tagged `Not Converted`, and retryable. The bookkeeping after it is ordered media → per-video metadata → index (the same "index last" rule as 6.3), so an interruption leaves an index that still describes what is on disk; the worst case is a converted video still wearing the `Not Converted` label, which is wrong on a label rather than lost.
  - **`Datastore::saveJsonArchive()`** — the single choke point through which the index and *every* metadata file is written. It had the identical bug on the most important file in the stash: an interrupted index save would have left the stash with no index at all, every video stranded. One line.

  `Crypto7z` deliberately does not reach for `Datastore::tmpfsWorkDir()` for its verification scratch space — `Datastore` depends on `Crypto7z`, and that dependency should not run both ways.

  Covered by smoke tests that pin the invariant (a failed `replace` leaves the original byte-for-byte intact, and leaves no `.new`/`.old` litter) including one that asserts the *old* behaviour of `encrypt()` so the difference cannot be forgotten, and by `dev/run_convert_check.sh`, which converts a real video through the real HTTP endpoint on a throwaway stash and checks it still decrypts, is now MP4/H.265, and left nothing behind.

- [x] 4.30 **Download a video back out of the stash** — `media.php?…&download=1`, with a Download button on the watch page. An oversight, and a bad one: videos could go in and never come out. Every archive is 7zip-encrypted with a password only the user knows, so the sole way to retrieve a video was the command line. The endpoint that already decrypts and streams now also sends the bytes as an attachment, named after the video's **title** rather than the stash's internal `1.mp4`. The title is the user's own free text and ends up in a response header and then on their filesystem, so everything that is not a letter, digit, space, dash or underscore is stripped from it — neither quotes, newlines nor path separators survive. The index is only opened on the download branch: `media.php` is called for every thumbnail on the wall, and decrypting the index each time to name a file nobody is saving would be waste.
- [x] 4.31 **Header and sort rework, and the missing favicon.**

  - **The nav moved into the header, before the search.** A whole band of chrome above the wall was a lot of vertical space for three links. The pills keep their class name (`category-bar`) so nothing that referenced them had to change.
  - **The search is centred between the nav and the action buttons**, not on the page's centre line. Worth stating because it was asked for and is not quite what was built: the brand plus three pills is about 550px wide, so a 640px box centred on the page would have to start at 430px and run underneath them. Centring it in the space that is actually free keeps the box full width and nothing overlaps.
  - **Upload and Filters lost their labels**, keeping the icon with the word as the `title` tooltip and the `aria-label`, so the control is still named for anyone not reading it visually.
  - **The sort is a menu, not a `<select>`.** The old control was an icon, the word "Sort" and a dropdown — a lot of toolbar for one setting. It is now a bare bordered icon that opens a menu on hover, built exactly like the user menu in the header. Each entry is a real link carrying the current filters and search, so a sorted, filtered wall stays a link somebody can keep, and sorting still works with scripting off. The Creators screen got the same treatment in the same commit: 5.9 deliberately made those two controls identical, so they change together.
  - **Below 1100px the wordmark and the pill labels drop out**, leaving icons with tooltips. Without that the header overflowed and pushed the user menu off the right edge.
  - **The favicon was simply missing.** Every page now declares `assets/img/icon.png`, and nginx serves `/favicon.ico` from the same file with the MIME map cleared for that location (the `.ico` in the URL would otherwise have labelled a PNG `image/x-icon`) — browsers ask for that fixed path whatever the pages declare, and it was falling through to `index.php` and answering with a redirect to the login page.

## Phase 5 — Search, Filter, Sort, Playlists

- [x] 5.1 Video search by title, creator and category tags, wired to the header search box — which appeared on every page but was connected to nothing. The term is a `q` in the query string handled by `App/src/VideoQuery.php`, so it composes with the filters and the sort and stays linkable. Several words all have to match but each may match a different field, so "jamie sport" finds a sport video credited to Jamie without either word matching both. Matching is case-insensitive and on substrings ("skat" finds "Skateboarding"), and runs against the already-decrypted index, so no video archive is opened to search. Searching from any page lands on the wall and deliberately carries no filters with it — the box searches the whole stash, and the filter panel is what narrows afterwards (it carries the term through). The count line and the empty state name the term, and a × in the box clears it.
- [x] 5.2 Creator filter — filtering the wall **by creator** (checkboxes in the filter panel) and now by a creator's *attributes* too: the age sliders and the gender menu were inert controls and are wired through `VideoQuery` like every other filter, carried in the query string so they stay linkable and compose with the search, the categories, the length range and the sort.

  The decisions worth recording:

  - **Age and gender belong to the creator, not the video**, so `VideoQuery::apply()` now takes the index's creator summaries alongside the video list — the video entries alone cannot answer the question.
  - **A video matches if *any* of its creators does.** On a co-credited video that is the only sensible reading: filter for a creator in her twenties and a video she made with someone older is still one of hers.
  - **An unrecorded age or gender does not match an active filter on that field.** An unknown age is not evidence of being in the range asked for — the same reasoning that puts unknown ages last in both directions of the 5.9 sort.
  - **The top of the age slider is an open end**, like the length slider's: at 80 it means "no upper limit", and the label says `any` rather than a number that reads like a real ceiling.
  - **The gender menu offers the values actually in use.** Gender is a free-text field on the creator form, so the old hard-coded Female/Male/Non-binary list could offer three options matching nobody while the gender someone actually typed was unofferable. It is now built from the creator records, compared case-insensitively, and a value arriving in the URL stays selectable so a linked filter never silently resets to Any.
- [x] 5.3 Video sort: title A→Z / Z→A, length short→long / long→short, views min→max / max→min, uploaded new→old / old→new — a sort menu on the wall toolbar, applied server-side (`App/src/VideoQuery.php`) so it composes with the filters and stays linkable
- [x] 5.4 **Playlists.** Parked earlier as not needed, then asked for with a design: a Playlists entry under the user profile, a screen of cards showing each list's name and first three videos, an edit screen where rows are dragged into order, an add-videos modal reusing the site's search, and a `Playlist +` dropdown on the watch page. Specified as SPECIFICATIONS.md §2.9.

  **Playlists are the one collection keyed by id rather than display name.** Categories and creators are keyed by name because that name *is* the reference a video holds — which is why `VideoCreators::rename()` has to walk every video and repoint it. Nothing references a playlist by name, so a rename is one field on one record, and two playlists may share a name. A name is a label here, not a key.

  **Membership is stored once, on the playlist.** A video carries no playlist field at all. The tempting symmetry — a list on each side — is two copies of one fact, and since the *ordering* has to live on the playlist regardless, the video's copy could only ever be the one that goes stale. "Which playlists hold this video?" is a scan of a few short arrays (`Playlists::containing()`), which is cheaper than the bug.

  **The order is the playlist**, so a drag and an add are the same write and share one endpoint: "this playlist now holds exactly these, in this order". The browser posts the whole order it is showing rather than a "move X above Y", which means a stale page stores what the user can actually see instead of replaying a move against a list that changed underneath it. Unknown ids are dropped and repeats collapse to their first position, so the endpoint cannot be talked into storing a video that does not exist.

  **Ids are never reused.** `nextId()` first computed the highest id still *present*, which hands the id straight back after deleting the newest playlist — and playlist ids appear in URLs, so a bookmark to a deleted list would open whatever was made after it. A smoke test caught it. The index now keeps a `playlist_seq` high-water mark that survives the delete, still maxed against the live records so a stash predating the counter cannot collide.

  **Deleting a video drops it from every playlist** in the same write (`forgetVideo()`). A playlist holding a video whose files are gone renders as a gap and silently changes what "5 videos" means. Deleting a playlist removes only the list — a playlist owns nothing on disk, which is why that can never cost a video.

  Smaller decisions worth keeping:

  - **The icon is real, not borrowed.** Sliced from `Docs/Assets/icons_v2.png` cell 16, which arrived on a white background — that turned out not to matter, since the amber keys off white as cleanly as off black. See `Docs/Assets/gemini_asset prompt.md` for the two ffmpeg passes.
  - **Not a fourth nav pill.** §4.2 fixes that bar at three destinations; a fourth would make it exactly what category names were kept out of it for. It goes in the user dropdown beside Manage Creators and Manage Categories.
  - **The watch page dropdown reuses `.sort-menu` wholesale**, so the site's three dropdowns open, close and sit the same way. A tick posts on its own — a dropdown that has to be confirmed is a dialog — and a newly ticked video is **appended**, because appending is the only insertion point that does not disturb an order the user arranged.
  - **The add-videos modal filters in the browser**, on the same three fields `VideoQuery::matchesSearch()` uses. The list is already decrypted for that page, so a round trip per keystroke would be slower and no more correct; matching the same fields is what keeps "search" meaning one thing across the site.
  - **A card stops at three videos** however long the list is. A card is for recognising a playlist; the whole thing is one click away, and a card that grew with its playlist would push the next one off the screen.
  - **`formatLength()` was two identical copies** — wall.php and video.php — and playlists wanted a third. Extracted to `App/views/format.php`. Three copies is where they start to drift, and a duration that reads differently on the wall than on the playlist it came from is the kind of difference nobody reports and everybody notices.

  **Not built, because it was not asked for:** play-all and shuffle. Playback is still one video at a time from the watch page.

  Covered by 28 smoke tests, `dev/run_playlist_check.sh` (20 checks over the real endpoints) and `dev/playwright/check_playlist.js` (15 checks), which exists for the one part no amount of curl reaches — that a row can actually be picked up and dropped somewhere else, and that the resulting order survives a reload. The browser half runs **last** in that script: it creates a playlist and ticks boxes, and run in the middle it quietly changed the contents the delete assertions below it were checking, which then failed for a reason that had nothing to do with deleting.
- [x] 5.5 View count tracking — `App/public/video_view.php`, called by the watch page when the player fires `playing` (not on page load, so opening a video without watching it doesn't count, and a file that fails to decode isn't counted as watched). The count is written to both the index entry and the per-video metadata, and the page updates in place.
- [x] 5.6 `uploaded_at` is now carried on each index entry (written at ingest, backfilled from per-video metadata by `migrate_records.php`), which is what "sort by uploaded" reads. Entries with no date sort oldest rather than jumping to the top.
- [x] 5.7 The filter panel filters for real: category checkboxes, creator checkboxes and the length range are applied server-side via the query string. The panel is titled "Filters" and its groups are `<details>` accordions — Categories (open by default) → Videos → Creators — where a group re-opens if it holds an active filter, so a filter can never hide behind a collapsed heading. Changing any control submits; there is no Apply or Reset (the "All Videos" pill is the reset, and a `<noscript>` Apply covers scripting being off). Because the filter lives in the URL, clicking a category on the Categories screen opens the wall filtered to it. The creator age/gender controls are still inert — that is 5.2.
- [x] 5.8 Creator search — matching a creator's name, bio or gender (`App/src/CreatorQuery.php`), with the same rules as the video search: case-insensitive substrings, every word has to match but each may match a different field. There is **one search box on the whole site** — the header one — and it searches whatever the page you are on is a list of: creators on the Creators screen, videos everywhere else. The count line and the empty state name the term, a x clears it, and opening a creator keeps the search and sort you got there with.
- [x] 5.9 Creator sort — name A→Z / Z→A, videos max→min / min→max, age young→old / old→young, in a menu matching the wall's. Applied server-side in `CreatorQuery` and carried in the URL, so it composes with the creator search and stays linkable. Creators with no age set sort last in *both* age directions rather than counting as age zero, and ties fall back to name order so the grid never shuffles arbitrarily.

- [x] 5.10 **Stats**, from the user menu (`App/public/stats.php`). Every video with its size on disk, largest first, and the stash total. The size is the whole video directory — archive, preview clip, thumbnail, metadata — because that is what deleting it would give back, and it is read off the filesystem on every load rather than stored, so a conversion cannot leave it stale.

  Points worth keeping:

  - **Inspect decrypts the whole video.** The archives are 7z with encrypted headers, so ffprobe cannot be handed just the head of the file, and an MP4 with its index at the end needs the end anyway. That is the cost of pressing play, so it runs in the request (`video_inspect.php`) — after `session_write_close()`, or every other page in that browser would queue behind the decrypt. The frame rate is `avg_frame_rate`, and width and height are as displayed: a phone clip with a 90° rotation tag reads portrait. The result is stored on the index entry and the per-video metadata (`fps`, `width`, `height`, `inspected_at`), and every conversion now records the same fields for the file it wrote.
  - **The reduce offer only appears for what an inspection measured.** 30fps is offered above 30.5fps, so 29.97 NTSC footage is not re-encoded for nothing. 1920×1080 is offered when either edge exceeds the box *turned the same way as the video* — a portrait 1080×1920 clip is at Full HD, not over it — and the scale keeps the aspect ratio and rounds to even dimensions. `video_reduce.php` re-checks both rules rather than trusting the ticked boxes.
  - **A reduction is a convert job with a `-vf` chain, not a new job kind.** The job id is what stops two ffmpeg runs replacing the same archive, and a separate kind would get a separate id and could run beside a plain Convert of the same video. It inherits everything 4.28/4.29 gave the convert: detached worker, progress card, write-verify-swap of the archive. The output is MP4/H.265 like any conversion.
  - `dev/run_stats_check.sh` drives inspect and a two-option reduction over HTTP against a throwaway 2560×1440 60fps stash, and probes the stored file afterwards: 1920×1080, 30fps, H.265. The smoke suite carries the rules, portrait cases included.

## Phase 6 — Password Change & Re-encryption

- [x] 6.1 Password change, from the Profile screen — `App/public/user.php` (which replaces the last static Phase 1 mockup, `user.html`) and `App/public/password_change.php`. The re-keying itself moved out of `bin/rekey_user.php` into `App/src/Rekey.php` so the form and the CLI run the same code; the script is now just the command-line way in, for a stash whose owner cannot log in to reach the form. The current password is checked against the one this session proved at login, and then re-proved the only authoritative way — by decrypting the index — before a single archive is touched; there is no stored password to compare against. A too-short, mismatched or unchanged new password is refused before any re-encryption happens. On success the session adopts the new password (`Session::setPassword()`, which also regenerates the session id) so the user stays logged in — without that, the next page load would find an index its key no longer opens and `refreshIndex()` would log them straight out. `Rekey` also now **rolls back** on failure, putting back every archive it had already rewritten; the old CLI script left a half-converted stash behind.
- [x] 6.2 Re-encryption pass (CLI — `App/bin/rekey_user.php {user} {old} {new}`; the web form is 6.1): for each video, decrypt with old password, re-encrypt with new password, keeping `{ID}.mp4.enc.old` until the whole run succeeds. Note this covers **all four** encrypted files per video (`.mp4.enc`, `.mp4.preview.enc`, `.jpg.preview.enc`, `.json.enc`), not just the video — the idea names only `.mp4.enc.old`, but every file is locked with the same password
- [x] 6.3 Update `{user}.json.enc` last, only after every other archive is re-encrypted — while the index still opens with the old password, an interrupted run is retryable. Implemented in `App/src/Rekey.php`; verified by moving the whole `TestUser` stash (11 archives) onto a 24-character password, and covered by a smoke test that re-keys a throwaway stash and checks it opens with the new password and no longer with the old.
- [x] 6.4 Cleanup of `.old` files on success. A failed re-encrypt now **rolls the whole run back** — it restores not just the archive that failed but every archive already rewritten, so a failure leaves the stash entirely on the old password rather than half-converted. (The original script restored only the failing archive and aborted, which left the earlier ones on the new key.) Covers all four files per video plus the creator archives, not just `.mp4.enc`.
- [x] 6.5 **Sessions are invalidated when the stash password changes.** `Session::refreshIndex()` used to fall back to its cached copy when the index would not decrypt; a session open across a re-key therefore kept writing every change back under the *old* password. That actually happened: a browser session left open during a `rekey_user.php` run rewrote the index and all three creator records under the old password while the video archives stayed on the new one, leaving the stash split across two keys. It now ends the session and sends the user to the login page with an explanation.
- [x] 6.6 **The re-key runs as a background job.** It used to hold the request open while 7zip rewrote every archive, propped up with `set_time_limit(0)` and `ignore_user_abort(true)`. That is fine for a handful of videos and wrong for a large stash: the browser sits on a blank pending request for minutes, any reverse proxy in front would time it out whatever PHP's own limit said, and a closed tab left no way to find out whether the run finished.

  `password_change.php` now validates and starts a job; `bin/job_worker.php` calls the same `Rekey::run()` it always did, with its `$onProgress` callback (now `(done, total, name)`, since the archive count is known up front) writing into the job record. The Profile page polls and shows "Re-encrypted 14 of 37 archives". No re-keying logic moved — that stays in one place.

  Two decisions worth recording:

  - **The rest of the site is locked while it runs**, and this is not a courtesy. Backgrounding the re-key reopened the failure 6.5 was written about: the session holds the *old* password, the worker is moving every archive to the new one with the index last, so a page load mid-run still decrypts fine and would cheerfully write something back under the old key — landing that one archive on a key the rest of the stash has already left. When the work was synchronous, the request itself was the lock. Now `Session::requireLogin()` is: while a re-key job is alive, every page but the Profile screen, the poll and logout redirects to the progress display.
  - **No session handover.** The session does not adopt the new password when the job finishes — a session holding a password the archives are not on is exactly the dangerous state — and the job outlives the request that started it anyway. When it completes the user is signed out and signs back in with the new password, which proves it worked.

  A second re-key cannot start while one is running: same job-id guard as 4.28, and unlike the disabled submit button, it is a real one.

## Phase 7 — Multi-user Support & Hardening

- [x] 7.0 **User creation flow** — `App/public/register.php` + `App/src/User.php`, linked from the login page. Creates `{user}/videos/{user}.json.enc` with an empty video list, a `default` creator and a `Not Converted` category (both required by ingestion), then signs the user straight in. Usernames are letters/digits only, max 32 chars, and must be unused; the same validation now guards `login.php`, which also closes the path-traversal hole in 7.1. Verified: symbols, traversal attempts, duplicates, empty and mismatched passwords all rejected; a new stash logs in isolated and empty.
- [x] 7.0.1 **Minimum password length: 24 characters**, enforced at registration (`User::MIN_PASSWORD_LENGTH`, checked server-side and hinted with `minlength` in the form). The password is the encryption key, is never stored, and cannot be reset or rate-limited at the archive itself — anyone with a copy of the `.7z` files can attack them offline — so length is the only defence. Login does not enforce the minimum, so stashes created before the rule still open.
- [x] 7.0.2 **Delete your stash, from the Profile screen** — `App/public/stash_delete.php`, `User::delete()`, and a danger card at the foot of `user.php`. Registration existed (7.0) with no way back out: a stash could only be removed by deleting `App/Data/{user}/` by hand, which is how the throwaway `HermanRas` account had to go.

  This is the most destructive thing the application can do, and unlike everything else there is nothing to restore from — a user *is* their directory, so there is no account record to disable instead and no copy kept anywhere. Four guards, each for a different mistake:

  - **Type the stash name to confirm.** A `confirm()` dialog is one keystroke away, and this should not be one keystroke away. The button stays disabled until the typed name matches exactly, and the server checks it again — the disabled button is a courtesy, the server check is the guard.
  - **The password is re-proved by decrypting the index**, not compared against the session. No password is stored anywhere to compare against, and a stash that cannot be opened is not one this code should be deleting. The same reasoning as the re-key in 6.1.
  - **The name is re-validated before it is used as a path.** It comes from the session, so it is already letters-and-digits — but it is about to be the last segment of a recursive delete, and that is worth checking twice rather than trusting. Covered by tests that try `../TestUser`, `Del/Probe`, `..` and the rest, and then assert `TestUser` is still there.
  - **Nothing may be running on the stash.** `Jobs::aliveFor()` refuses the delete while a convert or re-key worker is alive. This is not theoretical: a convert that finished after its throwaway stash had been removed recreated `videos/Video1/1.mp4.enc` under the deleted directory, because 7zip creates missing parents. `dev/run_convert_check.sh` now waits for workers before cleaning up, for the same reason.

  `Datastore::wipe()` skips what it cannot remove rather than throwing, so the directory is checked afterwards and a failure is reported as a failure — a stash reported deleted is one that is actually gone. On success the session is ended (there is nothing left for it to be a session of) and the login page says so; the name is free to use again.

  Covered by 20 smoke tests and `dev/run_delete_check.sh`, which drives the real form on a throwaway stash and expects the test to destroy it — the cleanup is a safety net for a failed run, not the normal path.

  What it has to get right, because this is the most destructive button in the app:

  - **It deletes everything and nothing can undo it.** No trash, no backup, no password on file to recover with — the videos, previews, creator records and index all go. The confirmation has to say that in those words rather than "are you sure?".
  - **Re-prove the password, not just a confirm dialog.** Require the current password and check it the authoritative way — by decrypting the index — exactly as `password_change.php` does. A session someone left open should not be enough to wipe a stash.
  - **Make the confirmation deliberate**: type the username to enable the button. A modal that only needs a click is one mis-click from an empty data directory.
  - **The target is `Session::user()` and never a request parameter.** The username must not be accepted from the form or the query string, or the endpoint becomes a way to delete somebody else's stash — the isolation concern 7.1 is about.
  - **Destroy the session and land on the login page** once the directory is gone, with a plain confirmation. `Datastore::wipe()` already removes a tree recursively; deleting the user directory should go through one place that refuses any path outside `App/Data/`.
  - Note what it is *not*: unlinking a file is not a secure erase, and the bytes may survive on the disk. That is acceptable here because everything in the directory is AES-encrypted with a password that was never stored — worth stating in the spec rather than implying.

- [x] 7.1 **Isolation between `App/Data/{user}/` datastores.** Traversal through `{user}` was closed in 7.0. Traversal through the *video id* was not, and it was exploitable: `video_delete.php` took `id` straight from the form post and handed it to `Datastore::videoDir()`, so a logged-in user posting `id=1/../../../OtherUser/videos/Video1` **permanently deleted another user's video**. Proved with two throwaway stashes before it was fixed, and the proof is now a test.

  The reason this one endpoint mattered so much more than the others is worth stating plainly: **deleting never decrypts anything.** Every other cross-stash reach — reading metadata, saving a title, adding a category — ends at a 7z archive that will not open without that user's password, so the encryption quietly did the access control. `unlink()` asks no such question. `video_category_add.php` and `video_category_delete.php` had the same missing check and were saved only by that accident, and would have failed *after* writing.

  Three layers, deliberately overlapping:

  - **The endpoints check the id against the index** before using it, which is the check `video_convert.php` already made and the others should have.
  - **`Datastore::videoDir()` and `creatorDir()` refuse anything but digits**, so an endpoint added later that forgets fails loudly instead of silently reaching into another stash. Ids are generated as integers and always come from the index, so this costs nothing legitimate.
  - **`Datastore::wipe()` refuses any path that does not resolve strictly inside `App/Data` or `/dev/shm`** — the roots themselves included, since they are never the thing being removed. This is the "one place that refuses any path outside `App/Data/`" that 7.0.2 asked for.

  Confirmed clean: `media.php` (`ctype_digit` on both the video id and the creator id, and the user always from the session), the wall, and job polling — `Jobs::id()` hashes the username in, so there is no id to guess. **Login gives a byte-identical response** for a wrong password and a user that does not exist, so it is not an existence oracle. Registration does still reveal that a username is taken, which is inherent in rejecting duplicates; accepted rather than fixed.

  Covered by `dev/run_isolation_check.sh` (14 checks), which runs one throwaway stash against another and judges every attempt by whether the victim's files changed on disk. It also asserts that a user can still delete their **own** video — isolation is trivially "fixed" by breaking deletion for everybody, and that must not pass.

  **A warning written in blood.** The first version of that script proved `wipe()` refuses `/app/src` by calling `wipe("/app/src")` and checking the directory survived. That is only safe if it refuses, which is the thing under test — and running it once with the guard temporarily reverted, to confirm the suite could still catch the bug it was written for, deleted `App/src` and the whole of `App/Data` for real. `App/src` was tracked and came back from git; `App/Data` is gitignored and did not. The refusal is now proved against sacrificial throwaway directories, with `Datastore::wipeWouldRefuse()` answering the question for real paths without deleting them. **Never point a destructive test at a directory you are not willing to lose.**
- [x] 7.2 **Command-injection review of every `exec`/`proc_open` call.** Four sites, and the verdict is that the app is sound — but it was verified rather than read, because "we use argv arrays" is exactly the kind of claim that stays in a comment after it stops being true.

  - **`Crypto7z::run()` and `VideoEncoder::run()` pass an argv array to `proc_open()`**, so no shell is involved and nothing a user types can become a command. The password matters most here: it is handed to 7z as `-p{password}` on every encrypt and extract, and it is chosen by the user. A stash whose password is nothing but `$(…)`, backticks, `;`, `|`, `&`, `<`, `>`, quotes and a newline now registers, stores and reopens correctly in the tests, with canary files proving none of it ran.
  - **`Jobs::spawn()` is the one place that does build a shell string**, because `setsid … &` genuinely needs a shell to detach the worker. It escapes each argument *and* the assembled command, and everything in it is a constant except the job id — which `Jobs::id()` builds as `{kind}-{16 hex}` from a hash, `job_status.php` allowlists the kind for, and `Jobs::path()` re-checks against a regex before it is used as a path. A crafted id dies with `Bad job id` before reaching the filesystem.
  - **Argument injection, not just shell injection.** An argv array stops the *shell* interpreting a value, but not the *program*: a filename beginning with `-` would be read by ffmpeg as an option, and one beginning with `@` by 7z as a listfile. Every path handed to either is absolute (`/app/Data/…` or a random `/dev/shm/…` work dir), so this cannot arise — worth stating, since it is the failure mode that survives the obvious fix.
  - **The uploaded filename never reaches a path intact.** `pathinfo()` takes the basename first, so `a.mp4/../../../../app/public/shell.php` yields `php`, not a traversal — and `VideoIngest::safeExtension()` now reduces it to letters and digits anyway.

  Covered by 14 smoke tests and `dev/run_injection_check.sh`, which pushes the same values through the real endpoints over HTTP and checks the canaries *inside the php container*, since that is where a command would have run.

- [x] 7.2.1 **What the audit turned up.** No injection — but three ways to lose an upload, all of them reachable from the upload form, and all of them leaving a mess behind.

  - **A `preview_at` past the end of the video destroyed the upload.** `upload.php` casts the field to a float with no bounds, and ffmpeg asked for a frame that does not exist writes no file while still exiting 0 — so the `encrypt()` of the missing preview threw, and the video was lost *after* being transferred in full. `VideoPreview::fromTimestamp()` refuses such a timestamp outright and is right to, because the user is on the edit screen and can be told; ingestion instead clamps it, because the video is already on disk and moving the frame is better than throwing the video away. A first-frame fallback covers what the clamp cannot foresee.
  - **An over-long extension did the same.** A 300-character extension made the staged filename longer than the 255 bytes the filesystem allows, so the upload failed at the staging step. `safeExtension()` caps it at 12 characters of letters and digits.
  - **Either failure left an orphan.** Because 3.10 claims the directory before writing into it, anything that threw afterwards left a part-written `Video{N}` holding megabytes of encrypted video — absent from the index, unreachable from every screen, impossible to delete from the UI, and permanently owning an id the claim loop then had to skip. Ingestion now takes the claim back down on any failure; the index is only written once `ingest()` returns, so a directory abandoned there is unreachable by definition and safe to remove.

  The one case that still fails is a file that is not a video at all, and it now fails cleanly — a real message, and no directory left behind.
- [x] 7.3 **Login throttling — and the timing oracle it turned up.** `App/src/LoginThrottle.php`, wired into `login.php` and `register.php`.

  **What rate-limiting a login does *not* do here**, since the usual reason does not apply: the password is the encryption key, is never stored, and there is nothing to compare a guess against. Anyone holding a copy of `App/Data` attacks the archives offline with none of this code involved. Length is the only defence there — 7.0.1.

  **What it does protect is the running service.** A failed login against an existing stash spawns 7z to attempt an AES decrypt: measured at ~130ms, against ~16ms for a name with no stash behind it. There are 16 php-fpm workers, and an unauthenticated attacker can spawn that work as fast as they can POST — the 4.28 lockup from a different direction. It also slows online guessing against stashes made before the 24-character minimum, which login deliberately still accepts so older stashes keep opening.

  **The timing oracle.** 7.1 checked that login answers identically for a wrong password and an unknown user, and it does — byte for byte. It does not answer in the same *time*: ~130ms against ~16ms, an eight-fold tell that enumerates usernames perfectly. `LoginThrottle::settle()` holds every failure to a 250ms floor, which levels the fast path up to the slow one and never adds to the slow one. Measured afterwards at 262ms against 262ms.

  Three decisions that follow from MyStash having no password reset and no administrator:

  - **Nothing is ever permanent.** A stash *is* its password; a lockout that did not expire on its own would mean the owner had no way back in. Every counter is windowed at ten minutes and ages out untouched. Ten rather than the more usual fifteen because the thing being locked is the owner's own access, and anyone who knows the username can trigger it.
  - **It refuses rather than sleeps.** Delaying a response holds a php-fpm worker, and with sixteen of them a delay long enough to matter *is* the denial of service it was meant to prevent. Past the limit the attempt is refused before anything is spawned: 9ms against 262ms, so a flood is roughly thirty times cheaper for the server to refuse than for the attacker to send. The 250ms floor is the one bounded exception.
  - **Attacking a lock cannot extend it.** Once a name is locked, further attempts are refused *before* anything is recorded, so no new failures accumulate and the window always closes on schedule. Otherwise anyone could hold the owner out indefinitely just by keeping at it.

  The correct password is refused too while a name is locked — necessary, or the lock is bypassable by exactly the party it exists to stop — so the page is told how many minutes to wait. A lock with no stated end, on an app with no password reset, is indistinguishable from a broken stash.

  **The address counter is a backstop, not a control.** Behind a reverse proxy every request can arrive from one apparent address — in the Docker setup they all come from the gateway — so it is close to global. It counts only *failures* for that reason: a counter ordinary successful use can fill is a lockout waiting to happen. A flood of *successful* registrations is therefore not throttled; the control for that is not exposing registration to the internet. A deployment that wants real per-client limits needs nginx's `real_ip` configured from a trusted proxy first.

  Covered by 11 smoke tests and `dev/run_throttle_check.sh` (9 checks), which drives the real endpoint and always clears the counter store on the way out — a check that left one behind would lock a real name out for real.
- [x] 7.4 **Final review against SPECIFICATIONS.md app flow (§2) for completeness.** Every numbered step and stated rule of §2 read against the code that implements it, then walked end to end over HTTP.

  **The flow is complete.** Nothing §2 describes is missing, and two things are stronger than it asks for. §2.2 only requires that the video file is not loaded until the user clicks play; the wall never references `type=video` at all, and even the watch page holds the source on a `data-video-src` attribute rather than the player's `src`, so opening a video page still fetches nothing. §2.1's step 2 ("check that path `./{user}` exists") is not a separate step in the code — a name with no stash simply fails to decrypt, which is the same answer step 4 already requires and one fewer thing to get wrong. 7.3 made that equivalence real by levelling the timing too.

  **Two places where the specification had fallen behind the code.** Both fixed in the document, not the code — the code was right in each case:

  - **§2.5 contradicted §3 on creator deletion.** §2.5 said deleting a creator reassigns their videos to `default`; §3 said it drops them from every video they were credited on, so a video credited to two people keeps the other. The code does what §3 says (`VideoCreators::remove()`), and `default` is reached only as the fallback for a video left with nobody. §2.5 now says that too. **The confirmation dialog's wording is deliberately left as it is** — that is a product decision, and it is not this review's to make.
  - **§2.6 said the in-app password-change form was "still to come".** It has been there since 6.1: `user.php` → `password_change.php` → `Rekey` as a background job (6.6), with `job_status.php` polled for progress. `App/bin/rekey_user.php` remains as the command-line entry to the same code, which is what makes an interrupted run retryable without a session.

  **`dev/run_flow_check.sh` (39 checks)** is what the review leaves behind. The other `dev/` scripts each prove one property in depth; this one is deliberately shallow and wide, following §2's numbered steps in the order a user meets them — register, log in, upload, wall, watch, tag, retire a tag — with every check naming the section it comes from. A specification is only worth what can be checked against it: a clause that nothing implements now shows up as a failing check rather than as prose that quietly stopped being true. It runs against a throwaway stash, and it clears the 7.3 counter store on the way out because its deliberate registration failures land in an address bucket that, behind this proxy, is shared with every real login.

  Two assertions in the first draft were worth nothing and were rewritten: a duplicate-category check that was the previous check reworded, and a negative grep for `type=video` with no positive control — a grep that finds nothing passes just as well against a typo, so the watch page is now checked to contain the string the wall is checked not to.
- [x] 7.5 **nginx in front of php-fpm, instead of PHP's built-in server.** `php -S` is explicitly documented as a development server and is single-threaded: it serves exactly one request at a time. That is the foundation under the 4.28 lockup, and it also means one video streaming through `media.php` blocks the page the user is trying to read. The compose service is still called `app` and still listens on 8080 — every bookmark and every `dev/playwright` check keeps working — but `app` is now nginx, with a `php` service behind it on FastCGI.

  Points worth keeping:

  - **php-fpm alone does not prevent "session lockups".** PHP takes an exclusive lock on the session file for the length of each request, so two requests from the same user still serialise however many workers exist — a progress poll would have queued behind whatever else that tab was doing. `job_status.php` calls `session_write_close()` the moment it has read the username, which is what actually fixes it.
  - **`fastcgi_buffering off`** on the PHP location: `media.php` streams decrypted video and serves range requests, and with buffering on nginx would stage the whole response before sending a byte, so seeking in a long video would stall until the entire file had been decrypted.
  - **`client_max_body_size 2G`** to match `php.ini`. nginx's default is 1M, which would have rejected every video upload before PHP ever saw it.
  - **`shm_size: 2gb`.** Docker's default `/dev/shm` is 64M, and every decrypt stages plaintext there — the extract dirs, the convert work dirs, the sessions, the job records. Anything much over about 50MB would simply have failed to extract. This was a live bug, not a new requirement.
  - **php-fpm runs as `www-data`, not root.** The bind-mounted `App/Data` is world-writable on the WSL mount so it needs nothing here, but on a real host it must be owned by that user. The `dev/*.sh` checks run their container-side PHP with `-u www-data` for the same reason: `/dev/shm` job and session directories are created 0700, and a root-created one would lock fpm out.
- [x] 7.6 **One container instead of two.** 7.5 split the stack into `app` (nginx) and `php` (php-fpm) talking FastCGI over the compose network. That split bought nothing: nginx here serves exactly one document root, out of the same files php-fpm executes, and neither is ever restarted, rebuilt or scaled without the other — so the second service was a second bind mount of the same code, a second image to keep in step, and a network hop between two processes that always live and die together. Both now run inside the `app` container, started by `App/docker-entrypoint.sh`, with `fastcgi_pass 127.0.0.1:9000`. The service is still called `app` and still listens on 8080, so every bookmark and every `dev/playwright` check keeps working; the `dev/*.sh` checks that ran `docker compose exec … php …` now say `app`.

  Points worth keeping:

  - **Half a container is the failure worth designing against.** The obvious entrypoint starts php-fpm in the background and execs nginx, and then php-fpm dying leaves nginx answering every page with a 502 while `docker compose ps` reports the service up. The entrypoint instead waits on both (`wait -n`) and exits as soon as either does, so the container dies and `restart: unless-stopped` means something.
  - **`STOPSIGNAL SIGQUIT`, inherited from `php:8.3-fpm`.** `docker compose stop` sends the image's stop signal, not SIGTERM. A trap on `TERM INT` alone therefore never fires: the stop was ten seconds of Docker's grace period followed by SIGKILL — a mid-write kill of the very process Docs/DEPLOY.md §7 tells you to stop cleanly before a backup. Measured, not assumed: 10.9s and exit 137 before the trap covered `QUIT`, 0.7s and exit 0 after.
  - **php-fpm is no longer on the compose network at all.** It listens on 127.0.0.1:9000 inside the container, so nothing outside can speak FastCGI to it — previously anything joined to `mystash_default`, the Playwright container included, could.
  - **The production overlay got shorter.** It used to override `ports` on one service and `volumes` on another; both now apply to the same service, so the read-only code mount, the writable `App/Data`, `php.prod.ini` and the loopback binding are one block. Verified by running it: `/app/src` read-only, `App/Data` writable, `display_errors Off`, `zend.exception_ignore_args On`, port bound to 127.0.0.1.
- [x] 7.7 **CI builds and publishes the container, and production runs what it published.** `.github/workflows/image.yml` builds the image, starts it, checks it serves the app, runs the smoke suite inside it and kills php-fpm to confirm the container goes down with it — and only then pushes `ghcr.io/hermanras/mystash:latest` and `:sha-<commit>`. `docker-compose.prod.yml` now pulls that image instead of building: `image:` with `build: !reset null`, and the base file's `./App:/app` mount replaced by the two paths a deployment actually needs from the host, `App/Data` and `php.prod.ini`. `MYSTASH_TAG` pins a commit, which is also the rollback.

  Points worth keeping:

  - **A Dockerfile that builds is a weaker claim than an image that answers.** The verification steps run against the built image before anything is pushed: `login.html` 200, `/` 302 (a 502 there is php-fpm dead behind a live nginx — invisible to a check that only asks nginx for a static file), the self-hosted font 200, both processes present, 227 smoke checks, and the container observed to exit when php-fpm is killed.
  - **Three repository problems only visible from a clean checkout**, found by running the workflow's steps against `git checkout-index` output rather than against the working tree. The entrypoint was not executable — this repository lives on a Windows drive mount where git has `core.filemode=false` and had recorded every script as 0644, so the container exited 126 on "permission denied"; fixed in the index and with `COPY --chmod=0755` so the image cannot depend on that being remembered. The smoke suite was not self-contained: one check asserted that a `../TestUser` traversal had not deleted `TestUser`, a stash that does not exist on a fresh clone — and which, on any machine where it was simply absent, would have passed vacuously, because a directory that was never there cannot be observed to survive; it now creates its own bystander to traverse at. And `docker-compose.yml` now names the image, so CI can bring the stack up with `--no-build` and know it is testing the image it is about to publish.
  - **Two things only the real runner could show.** `github.repository_owner` is `HermanRas`, and Docker repository names must be lowercase — the first run failed on the tag. The name is now derived with `${GITHUB_REPOSITORY_OWNER,,}` rather than hardcoded, so a fork publishes under its own owner. The four actions were also a major version behind and being forced off Node 20.
  - **Not mounting the code is a stronger position than mounting it read-only.** The image's code is root-owned and 0755 while php-fpm runs as `www-data`, so the web root is unwritable by the process serving it, and there is no path from a file placed in a container layer to the host at all.
  - **The `./App` mount is what made development work, and exactly what production must not have.** Left in place it would put the deployment host's working tree straight over the image that was just pulled — the image would be downloaded, started, and then completely bypassed.

## Phase 8 — v2.0.0: libsodium at rest

- [x] 8.1 **Every archive moves from 7-Zip (`.enc`) to libsodium (`.epc`).** `App/src/StashCrypto.php` writes and reads the new format — XChaCha20-Poly1305 secretstream over 1 MiB chunks, the file name in an authenticated first frame — behind the same `encrypt` / `extract` / `replace` surface `Crypto7z` had, so the callers changed in name only. `App/src/StashKey.php` turns the password into the key with Argon2id (libsodium MODERATE: 256 MB, ~0.5 s) and a per-stash salt written into every archive header. Format in SPECIFICATIONS §3.1; rationale and upgrade in Docs/v2_migration.md.

  Points worth keeping:

  - **The cipher was never the weak point.** AES-256 is not what anyone breaks. What v2 fixes is around it: 7-Zip had no authentication (a changed byte decrypted into changed data), hashed the password with fast unsalted SHA-256, and took it as `-p<password>` on the command line of every encrypt and decrypt, where `ps` could read it.
  - **The session holds the key, not the password.** Argon2id costs half a second, so it runs once, at login, and the derived key travels as a token through the session and the job key files. Places that used to compare a typed password against the session (password change, stash delete) now re-derive and compare keys (`StashKey::matches`). A re-key hands its job the current *key* and the new password, never the current password.
  - **The username oracle had to be closed again.** Argon2id made a wrong password cost ~0.5 s and an unknown name ~0 s — far past the 250 ms floor from 7.3. `StashKey::unlock()` now derives against a throwaway salt when there is no stash, so both paths pay the same work. Measured over HTTP: 0.37 s against 0.40 s.
  - **Salt and cost live in every header, not a side file.** Any single archive can be decrypted on its own, nothing extra can be lost, and `tools/decode.php` — standalone, repo only, not in the image — needs no app code at all. Its tests run it in a stock `php:8.3-cli` container against a stash the app wrote.
  - **The upgrade is a one-time job on first sign-in** (`App/src/MigrateV2.php`, `public/upgrade.php`, `bin/migrate_v2.php`). It never touches a `.enc` until every `.epc` is written and proven byte-identical; the v2 index is written last and is the "this stash is v2" marker, so an interrupted run is simply run again. The tests prove the rollback on an unreadable archive, a stale `.epc` from a crashed run, a re-run after completion and the leftovers of a crash during cleanup.
  - **Measured before choosing:** ultra 7-Zip compression (`-mx=9`) on a 144 MB H.264 file saved 0.002% for a 31× slower encrypt and 3× slower decrypt, and made a JPEG bigger. Archives stay uncompressed.
